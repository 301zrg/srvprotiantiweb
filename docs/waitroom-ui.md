# 决斗准备页与手动准备

2026-10-07 的调整覆盖侧栏文字溢出、手机准备页难操作、准备／退出按钮难辨认，以及入房自动准备。

## 当前行为

- 入房默认未准备，首次展示和选择本地卡组不发送 `UPDATE_DECK` 或 `HS_READY`。服务器模式的 Core 在第一次收到 `UPDATE_DECK` 时会调用 `PlayerReady(true)`，因此仅在用户点击「准备决斗」时才上传选中卡组并发送准备；换备仍按原来的协议提交，不受这个等待页约束。
- 「准备决斗」使用蓝色主按钮和勾号，已准备后变成「取消准备」；玩家卡片另显示文字状态。已准备时改选卡组只发送取消准备，新卡组继续留在本地，需再次手动确认。
- 等待服务器确认准备／取消期间显示加载状态，准备状态以服务端消息为准。没有卡组、身份未确认或正在观战时不能准备。卡组选择受控，展示主／额外／副卡组数量，空卡组列表不崩溃。
- 退出房间及聊天按钮直接显示图标与完整文字，取消原先悬停展开窄按钮的做法。桌面收起聊天真正释放侧栏宽度；手机聊天使用可触摸关闭的面板，关闭期间继续接收消息，并保留未发送草稿。
- 手机内容区可独立滚动，底部准备／开始操作保持可见。语言选择移到准备页顶部，避免挡住底部按钮；猜拳和先后手选项可换行，触摸目标至少 44 CSS px。
- 开始按钮仅在房主、所需席位全部有人且全部准备时启用。Single／Match 使用两个席位；Tag 使用四个席位，A 队为第 1／2 席，B 队为第 3／4 席。第 3／4 席的准备、取消、退出、转观战和移动状态不再被忽略；同席移动不清空玩家。

## 双打支持范围

此前首版只实现／验收双人 Single、普通 Match 与 TT Match，Tag 完整对局没有纳入已完成范围；旧准备页只检查两位玩家。现在补齐 **Tag 等待页、四席状态和全员准备条件**，这不能当作完整双打已经可用。

双打队友轮换协议（例如 `MSG_TAG_SWAP`）、行动者与队伍身份、队友手牌／卡组切换、计时与观战视角仍需单独适配，并以四个原生／网页客户端联调和完整比赛验收。页面提示此限制，发布说明也不将双打实战标成通过。服务器仍独立判断人数和准备状态，不修改服务器的四人开局要求。

## 本地回归

```powershell
npm run test:waitroom-ui
npm run test:local-wss
```

`test:waitroom-ui` 使用本地 Vite、Edge 和模拟房间，不连接正式服务器。覆盖 390×844、844×390、568×320、320×640、1280×800：

- 入场不上传卡组；选择卡组不隐式准备；确认、取消和准备后换卡组的实际发包顺序。
- 准备、退出、聊天及开始按钮在可用视口内，手机触摸目标足够大；桌面侧栏收起／展开，手机聊天关闭、草稿与后台接收消息。
- 观战／决斗者切换；四席的缺人、未准备、取消、离开、转观战、移动与非房主不可开局。
- 四语切换与屏幕旋转保持卡组选择和服务端准备状态；猜拳及先后手选项可触摸，并发送正确协议值。

上述五种视口检查通过，普通双人房的玩家卡片与底部操作同时完整显示；较小横屏精简卡组数量提示，完整卡组信息在其他视口保留。截图与结果保存在不提交的 `.audit-tmp/waitroom-ui/before/`、`after/`，本机对照报告为 `.audit-tmp/waitroom-ui/report.html`；真实 Android／iOS 键盘、浏览器后台恢复和完整双打实战仍需另验。`test:local-wss` 的准备检查已经改为先断言双方未准备，再主动点击，不能再兼容入场自动准备而掩盖问题。

隔离真实 Core 的普通房开局、弃权结束及首次重新入场，TT G1–G3、两次换备和退出保留昵称／密码均通过；类型检查、lint 与构建通过。此自动弃权回归验证生命周期，不能代替正常完整比赛、完整双打或手机真机验收。当前公网测试隧道仅检查可信 TLS／WSS 101，通过后关闭连接，没有提交入房或对局消息。

更新只涉及网页；重新构建并上传新的静态包后生效，准备页修改无需重启 SRVPro、Nginx 或隧道。独立的禁表修正仍按 [禁表替换步骤](banlist-diagnosis.md) 执行。
