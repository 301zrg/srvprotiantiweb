# 海外操作等待与补时方案

更新：2026-10-10。用户反馈主要是「对局中点击操作后等待久」，目标用户以日本、韩国为主。本次只修改网页诊断；服务器计时、Core、隧道配置均未修改。

## 当前可确认的事

网页脚本、四语卡库、音效由外部静态托管加载；页面启动后，操作经浏览器已经建立的 WSS 直接发送，不会每点击一次先回到静态站点再转发。当前公开配置指向 Cloudflare Quick Tunnel，因此对战路径仍经过 Cloudflare 网络、服务器 cloudflared、本机网关和 Neos。更换静态托管本身不能证明对战链路会改善。

本机读取 [正式版本](https://ocg1103nexus.com/deployment-info.json) 得到 `fb6f6f563c625ff5cfebf83c2bc4a359b69fe6cb`；公开 WSS 信任证书与 101 握手四次通过，耗时 1069、990、804、766 ms。这些值包含 DNS／TCP／TLS／升级，仅代表本机建立连接的时间，不是持续对战 RTT，也不能代表日本／韩国运营商。PR #24 的展示延长当时尚未上线，不能解释已有反馈。

从代码可以确认两类等待都存在：WSS 跨境链路，以及在线消息保序执行并等待卡片动画。后台回来或手机慢消费时还可能积压。缺少海外实战的操作／到达时间证据，目前不能断言其中哪一段是主因；也不能从玩家 IP 模拟其当地线路。提供的玩家列表不会随代码或文档发布。

## 网页连接诊断

设置 → 操作 → 查看连接诊断，可复制最近 30 次已发送 RESPONSE 的时间样本。仅内存保存，本连接结束／换连接后不沿用；不含昵称、密码、房名、卡号、原始封包、URL 或自动上报。查看按钮每次重新生成快照。

| 字段 | 含义及限制 |
| --- | --- |
| `queuedAtSend` | 发送时尚在本机处理队列中的 WebSocket 消息与帧数之和；两个计数单位不同，仅用于判断是否积压 |
| `timeToFirstMessageMs` | 发操作后到下一条 WebSocket 消息到达；可能是聊天／另一消息，并非明确操作回执，不能当 RTT |
| `firstMessageQueueMs` | 上述消息到达后，到开始处理这条消息的本机等待，包含此前动画或弹窗等待 |
| `maxFrameQueueMs` | 操作后新消息已到达、到开始处理其中某一帧的最长本机等待；覆盖同一条粘包消息内前面的动画，截止于下一条 Core 交互请求。发送前就已到达的消息不归入此操作 |
| `timeToNextPromptMs` | 发操作后，到开始处理下一条 Core 交互请求；包含网络、裁定及先前展示，可能是其他玩家的请求，并非自己已经能操作 |
| `queuedNow` | 查看时的本机队列数量，口径同 `queuedAtSend` |

缺字段表示没有观察到该阶段，不能补成 0。样本不记录确认框内的犹豫时间，因为起点是实际发送。第一条消息排队短也不证明之后所有动画都很快；必须结合下一请求的时间和实际画面。

建议日本、韩国各至少两位玩家在原来卡顿的网络上完成十余次操作后复制结果，说明当地时间、设备／浏览器、Wi-Fi 或移动网络、是否使用代理、正常或卡顿。不需要提供个人 IP 或录像。对比同一时段、同一设备的网页与原生客户端，避免把不同对局、不同代理或不同时间的结果直接比较。

## 优化优先顺序

1. **网络等待为主：** 核对服务器 cloudflared 日志的重连／错误、实际协议与服务器 CPU；在不影响正在进行的对局的维护窗口对比 `auto`／`quic`／`http2`。现有 PM2 包装已支持 `NEOS_TUNNEL_PROTOCOL`，不需先改代码。QUIC 与 HTTP/2 谁更快必须当地实测；改变协议会重启隧道并改变 Quick Tunnel 地址，不能当作无感热更。
2. **持续公网使用：** 条件允许时换正式命名隧道以稳定地址和运维。Quick Tunnel 无 uptime 保证，有 200 个同时在途请求上限；这不是已经确认的本次卡顿原因。正式隧道也不保证自动降低 RTT。[官方限制](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
3. **队列等待为主：** 先用现有动画速度设置做同设备对照，避免后台放置。用户已决定保留连续动画，本轮不加累计队列上限、不快进或跳过在线消息。只在明确定位某个异常慢的展示后另行修复。
4. **仍无法改善：** 可评估香港／东京等地的 WSS 中继，静态站点保持现状。需要独立服务器、证书、运维和真实客户端 IP 的可信传递，还须验证中继→当前大陆服务器链路及国内玩家影响；不能仅凭地理位置承诺更快。未部署或新增费用。

`--protocol auto` 默认选择 QUIC，在 UDP 无法建立连接时可回退 HTTP/2；不能把它理解为按实时延迟自动选择最优协议。官方 `--region` 当前仅提供 `us` 或默认全球，不能填写 `jp`／`kr` 来强制东京／首尔。详情见 [运行参数](https://developers.cloudflare.com/tunnel/reference/run-parameters/)。本轮不切换生产协议，不新增心跳假包，不自动重放操作。

## 当前计时与已有补偿

计时裁定在服务端原生 YGOPro，不在浏览器。网页 [timeLimit.ts](../src/service/duel/timeLimit.ts) 收到己方 TIME_LIMIT 后按原协议发送 TIME_CONFIRM；不会报告一个自己想要的剩余时间。

只读核对相邻项目 `srvprotianti/ygopro/gframe/single_duel.cpp`、`tag_duel.cpp`、`netserver.cpp` 与 `ygopro-server.coffee`：

- 原生 TimerTick 在等待响应期间累计，TimeConfirm 对小于 10 秒且未超补偿预算的等候免扣；补偿预算由宿主时间初始化，后续按现有规则恢复。
- 合格的响应会返还 1 秒，但有 `time_backed` 预算、宿主上限；重试、SELECT_UNSELECT_CARD、连锁不发动及部分阶段／洗牌操作不返还。不是每次点 UI 都可以加时。
- 网页保序消费可能把 TIME_LIMIT 确认也放在此前动画后面；小于 10 秒的既有补偿可缓解一部分，但不能保证覆盖长时间后台或所有高延迟。
- 源码存在补偿不等于正式服务器二进制必然是这一版。需要维护者核对部署来源，未读取私有配置或替换正式二进制。

## 如果线路仍慢，怎样补时

| 方案 | 能否近期采用 | 影响及代价 |
| --- | --- | --- |
| 普通朋友房使用更长时间 | 无服务器代码改动／无需重启 | 两人输入同一个 `TIME5#房名`，或 Match 的 `M,TIME5#房名`，前缀 5 为 5 分钟。仅适用普通房，不替换 TT，不延长已开始的房间 |
| 新天梯房统一放宽时间 | 优先建议的小改配置 | 可先评估从现值增加 60–120 秒；两边同规则。实际基线由维护者确认，默认样例为 180 秒。本地宿主启动时读 `hostinfo.time_limit`，未实现此项热更，因此现状需要安排重启，对新创建房间生效 |
| 新房间时间配置热更 | 后续最小服务端开发方案 | 宿主提供通用、带校验和最后有效值保留的时间配置，TT 只决定是否采用；创建房间冻结快照，不改在玩房间。首次部署这种能力仍需要重启，此后调值可不重启。未实现 |
| 按实测延迟自动补偿 | 后续方案，改动较大 | 服务端计时器必须接受受约束的预算；网页调数字无效。需要可靠测量、防滥用、双打／重连／原生客户端兼容和真实对局回归。未实现 |

自动补偿建议按连接实际表现，而不是日本／韩国身份或国家 IP。可设计独立的、服务端挑战与回显的测量通道，绑定当前连接，避免向现有 YGOPro 二进制流插入 JSON。不能信任前端自己上报 RTT；TIME_LIMIT→TIME_CONFIRM 又包含动画／后台等待，不能直接当纯网络 RTT。

若以后实施，先讨论明确预算：例如每次请求最多 1 秒、每回合最多 30 秒、整场再设总限额；用一段时间内的较低延迟分位数估计稳定链路，配硬截止，防止故意慢回包换取思考时间。上述数值是待讨论起点，不是已修改的规则。无测量、断线、重连不发重复奖励，不能冻结对手计时；保留现有原生补偿，避免两层重复发放。

近期建议先部署网页诊断收集海外实战样本。若确认网络难以改善，再决定是否统一增加时间；本次不改服务器或要求立即重启。
